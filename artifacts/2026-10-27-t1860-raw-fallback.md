# T-1860: raw-transcript fallback (retrieval-only measurement)

Date: 2026-10-27. Scope: when claims do not answer, fall back to the operator's raw
local Claude Code transcripts and return dated, cited fragments.

## What shipped

| Piece | Where |
|---|---|
| Sidecar FTS5 index (never the claims DB, never creates claims) | `memorymaster/recall/transcript_index.py`, default `~/.memorymaster/transcripts.db` (`MEMORYMASTER_TRANSCRIPT_INDEX` overrides) |
| Opt-in CLI (no `MemoryService`, nothing runs unless invoked) | `memorymaster transcript-index`, `memorymaster transcript-search` (`memorymaster/surfaces/cli_handlers_transcripts.py`) |
| Benchmark (no LLM) | `scripts/bench_transcript_fallback.py` |
| Tests (synthetic JSONL, tmp dirs) | `tests/test_transcript_index.py` |

Reuse: the existing `verbatim_memories` store (`recall/verbatim_store.py`, `search_verbatim`
MCP tool, `recall/verbatim_recall.py`) lives inside the authoritative DB, is filled by the
stop hook only, never stores the per-message transcript timestamp, has no incremental file
tracking and no project scope. It was left untouched; the new index reuses its approach (FTS5
`porter unicode61`), `open_conn`, `recall_tokenizer._candidate_tokens`,
`core.security.sanitize_persisted_text` (display redaction) and `core.scope_utils.scope_from_cwd`.
No embedding model is involved (FTS5 only), so indexing is one cheap process.

Behaviour: each fragment (~1800 chars of consecutive user/assistant text) carries an ISO UTC
date (first message's `timestamp`), the opaque session id (`sha256(project-dir/file)[:16]`,
same as the T-1817 bench id: the encoded project directory, which can contain a username, is
never stored), the project scope (from the transcript's `cwd`) and the 0-based JSONL line
range. Ranking: BM25 relevance first; inside one 5% relevance band the newest date wins.
Incremental: unchanged files skipped, appended files parsed from the stored byte offset,
shrunk/rewritten files rebuilt, a half-written last line retried next run.

## Measurement (40 T-1817 questions, retrieval-only)

Index: transcripts modified in the last 9 days (643 files, about 1.0 GB of JSONL) -> 10,906
fragments, 29 MB sidecar. First index 8.5 s; re-run with nothing new 0.6 s. Claims DB opened
through `MemoryService(read_only=True)` (legacy retrieval, top 5, one fresh service per
query, as in T-1817). Transcript root read-only. Proxy metric: answer-token recall of the gold
answer (tokens `[A-Za-z0-9_-]{4,}`) in the retrieved text; "answered" = recall >= 0.5;
"evidence hit" = a fragment covers the question's evidence session + line. Latency =
wall-clock per retrieval call over the 40 queries.

Leak control: the T-1817 harness ran its answer/judge calls as Claude sessions, so their
transcripts quote every question and gold answer. Without filtering the fallback "wins" by
reading the answer key (85% answered, 0% evidence hit). The table below excludes fragments
that quote a question, a gold-answer prefix or a harness marker (except the fragment covering
the question's own evidence line).

| Arm | Items | Mean token recall | Answered (>=0.5) | Evidence hit | p50 ms | p95 ms |
|---|---|---|---|---|---|---|
| claims alone | 5 | 0.213 | 5.0% | 0.0% (claims carry no line) | 72.3 | 224.6 |
| fallback alone (transcripts) | 5 | 0.527 | 50.0% | 25.0% | 10.9 | 18.5 |
| union5 (interleaved, same 5-item budget as T-1817) | 5 | 0.372 | 22.5% | 2.5% | 82.6 | 236.1 |
| **claims + fallback** (claims then fragments) | 10 | **0.586** | **57.5%** | 25.0% | 82.6 | 236.1 |

Unfiltered (leaky) run for reference: fallback 85.0% answered / 0.0% evidence hit,
claims+fallback 87.5% answered. Not a valid result; shown only to make the contamination visible.

Caveats (read before quoting):
- Proxy, not the LLM-judged correctness of T-1817 (12.5% claims, 30% union). It measures
  whether the answer's words are in the context, not whether a model would answer correctly.
- The 40 questions were generated from the last-week transcripts, so the index window was cut
  to match (9 days). A full-history index (31k files, 28 GB on this machine) was NOT built.
- Claims latency includes constructing a read-only `MemoryService` per query (T-1817 method);
  a long-lived server would pay less. The fallback p50 of about 11 ms is the shipped CLI path.
- `union5` loses to `claims+fallback` because 5 slots dilute the better arm; the fallback is
  meant to be appended when claims come back empty or weak, not interleaved.
- Questions are biased toward things that were said in conversation, which favours raw search.

## Known limits
- The sidecar stores transcript text as written (it lives next to the transcripts the operator
  already holds); redaction (secrets, encoded secrets, home paths) runs on displayed text only.
  Do not copy or share the sidecar file.
- Project scope comes from the transcript's `cwd` basename via `scope_from_cwd`; a session whose
  cwd is a bare home directory would surface as `project:<folder-name>`. In the 9-day window
  indexed here every scope was a repository or automation-run name.
- A first run over the full history (28 GB here) was not attempted; use `--since-days` / `--max-files`.

## Not done / follow-ups
- No MCP tool: raw transcripts are higher-risk than claims (no per-claim sensitivity gate);
  exposing them to every MCP client needs its own decision. CLI only.
- No dense/rerank stage: FTS proxy was already 50% answered; adding an embedding process was
  out of scope for the load constraint.
- Automated-agent sessions (e.g. `claude -p` harness calls) are indexed like any other; a
  future filter could skip them by directory or marker.
